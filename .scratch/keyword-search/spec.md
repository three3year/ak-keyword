# 規格:幹員關鍵字搜尋

Status: ready-for-agent

## 需要你決定的

### 台服模式下，模組3 階段的敘述從哪來?

決定(2026-10-19):(a)用陸服簡中，只列台服已實裝的模組。

台服資料庫(arknights-data-tw-for-maa)只有模組清單(`uniequip_table`)，沒有模組改寫特性與天賦的那張表(`battle_equip_table`)。因此台服沒有模組3 階段的官方繁中敘述，也無法確認台服的模組數值。見[伺服器文字選擇](#伺服器文字選擇)。

- (a)用陸服簡中，只列台服已實裝的模組(建議):依台服模組清單判斷模組有沒有出，文字與數值取陸服，並標「陸服資料」。代價:台服數值若和陸服不同，會顯示陸服的數字。
- (b)台服模式不提供模組3 階段:天賦與特性只比對、只顯示無模組階段。代價:只靠模組才有的效果在台服模式搜不到。

### 效果類型的判定方式要寫成 ADR 嗎?

決定(2026-10-19):(a)寫成 ADR，見 `docs/adr/0001-effect-type-rules-plus-session-llm-review.md`。

「先用規則自動判定，只有新增或變動的敘述在 Claude Code session 裡交給 LLM 複核，結果寫進覆寫檔，不呼叫 API」。這個做法事後不容易改，沒看過討論的人也會納悶為什麼這樣做。見[效果類型判定](#效果類型判定)。

- (a)寫成 `docs/adr/0001`(建議):一段話記下背景與取捨。代價:多一份文件。
- (b)不寫:只留在本規格裡。代價:規格歸檔後，理由就散失了。

## 問題陳述

明日方舟的幹員有數百位，每位都有技能、天賦、特性、模組敘述，裡面寫著寒冷、凍結、浮空這類效果。玩家想知道「誰能上寒冷」、「誰能同時上浮空和法術脆弱」時，只能一位一位點開敘述來讀。現有的工具站(例如 arkntools.app)有公開招募、材料、基建技能篩選，但沒有依技能與天賦效果找幹員的功能。玩家還想用繁中閱讀，又想同時知道台服目前有沒有這位幹員。

## 解決方案

做一個純前端的網頁，部署在 GitHub Pages，手機也能用。使用者從分組的關鍵字面板點一個或多個關鍵字，網頁就列出同時具備這些關鍵字的幹員。

每位幹員顯示頭像、名字和命中敘述:關鍵字會高亮，並標出敘述來源、階段、效果類型(施加/利用/抵抗/其他)。使用者可以切換陸服或台服、依效果類型、星級、職業與分支篩選。懸停在關鍵字上可以看術語的官方定義。

資料在本機建置時就從陸服與台服的遊戲資料抽成小型索引，所以網頁不需要後端，開啟很快。

2. 身為玩家，我想同時選多個關鍵字，只列出全部都具備的幹員，這樣能找到特定的效果組合(例如浮空加法術脆弱)。
3. 身為玩家，我想讓關鍵字面板依類別分組(控場、減益、增益、元素傷害等)，這樣在五、六十個關鍵字裡也找得到想要的。
4. 身為玩家，我想在面板上方打字過濾關鍵字，這樣能直接找到已知名稱的效果。
5. 身為玩家，我想看到遊戲術語以外的常用效果(擊退、拉拽、沉默、減速)，這樣常見的問題也能查。
6. 身為玩家，我想在懸停或點開關鍵字時看到官方定義(例如寒冷「攻擊速度下降，持續時間內再次受到寒冷則變為凍結」)，這樣不用另外查效果的意思。
7. 身為玩家，我想看到補充關鍵字的簡短說明，並且明確標「非官方」，這樣能分辨哪些是官方定義。
8. 身為玩家，我想直接點命中敘述裡高亮的關鍵字，把它加入或移出選擇，這樣能從結果延伸查詢。
9. 身為玩家，我想一鍵清除所有已選關鍵字，這樣重新查詢很方便。
10. 身為玩家，我想讓遊戲新版本出現的新術語也能被搜尋，即使它還沒歸進任何分組，這樣搜尋不會漏掉新效果。

11. 身為玩家，我想看到每段命中敘述與關鍵字的關係(施加、利用、抵抗、其他)，這樣能分辨「會上寒冷」和「打寒冷敵人比較痛」。
12. 身為玩家，我想用複選框選擇要看的效果類型，可以只勾一種，也可以勾多種，這樣能縮小或放寬結果。

### 敘述範圍

15. 身為玩家，我想讓技能、天賦、特性、模組的敘述都納入搜尋，這樣來自特性或模組的效果也找得到。
16. 身為玩家，我想讓召喚物技能裡的效果也算在所屬幹員名下，並標「召喚物」，這樣只靠召喚物上寒冷的幹員也會出現。

20. 身為玩家，我想讓天賦與特性的無模組與模組3兩個階段都參與比對並列顯示，這樣只靠模組才有的效果也搜得到。

## 實作決策

### 架構

- 純前端網頁，以 Vue 3、Vite、TypeScript 撰寫，打包成靜態檔部署到 GitHub Pages;沒有後端。開發與驗收都在本機進行(Vite 本機預覽);部署由使用者在全部完成後自行處理。
- 分兩段:本機執行的**索引建置**，和瀏覽器裡執行的**查詢**與介面。兩者唯一的交界是索引 JSON。
- 搜尋與篩選全部在瀏覽器裡對索引進行。索引只含需要的欄位，目標是數百 KB 等級。

### 原始資料

- 陸服:Kengxxiao/ArknightsGameData 的 `zh_CN` 遊戲資料(幹員表、技能表、模組清單、模組戰鬥資料、阿米婭形態表、遊戲常數中的術語字典)。
- 台服:arkntools/arknights-data-tw-for-maa(幹員表、技能表、模組清單、阿米婭形態表、遊戲常數)。這個資料庫沒有模組戰鬥資料，所以模組3 階段一律用陸服資料，見[伺服器文字選擇](#伺服器文字選擇)。
- 頭像:建置時從公開的遊戲資源庫下載並壓縮成小圖，隨網頁部署。來源在實作時選定，需要能以幹員 id 對應。
- 建置會記錄兩邊的資料版本號，寫進索引。

### 敘述解析

- 遊戲文字的標記分兩種:術語標記(帶術語 key，例如寒冷)與樣式標記(只影響顏色)。解析器要處理巢狀標記、術語標記包住【】括號的寫法，以及「<替身>」這種不是標記的角括號純文字。
- 佔位符要以對應的數值表(blackboard)填入實際數值，並依格式符號轉成百分比或小數。數值表的 key 名稱不代表效果種類，不能拿來判斷效果。
- 解析後的敘述保留術語位置，供介面高亮與懸停定義使用。
- 遇到無法辨識的標記或找不到數值的佔位符時，建置輸出警告。

### 階段展開

- 技能:取等級7與專精3兩個版本;沒有專精的技能只取其最高等級。
- 天賦:無模組階段取精英二、潛能1 的版本。潛能加成沿用遊戲文字中的加成標記組成「A(+B)」，B 對應的潛能等級取自該天賦版本的潛能需求。
- 特性與天賦的模組3 階段:每個模組各取第3級的改寫結果，並記錄模組名。
- 召喚物:依幹員表中幹員與召喚物的對應，把召喚物的技能與天賦歸到所屬幹員，敘述來源標「召喚物」。
- 阿米婭的各職業形態各自成為一位幹員，職業依形態而定。

### 關鍵字

- 關鍵字分兩種來源:**術語**(遊戲術語字典中的戰鬥術語，自動隨資料更新)與**補充關鍵字**(維護者清單)。
- 術語以術語 key 比對，所以不受陸服、台服譯名不同的影響。補充關鍵字以清單中的簡中與繁中字串比對純文字，比對時排除已在術語標記內的文字。
- 關鍵字顯示名稱優先用台服術語名，台服沒有該術語時用陸服名。
- 關鍵字分組由維護者清單決定，沒有列入的關鍵字歸到「未分組」。

### 效果類型判定

- 判定的單位是「一段敘述 × 一個關鍵字」的配對，結果為施加、利用、抵抗、其他之一。
- 先用句型規則判定。例如「使…陷入 X」「造成…X」判為施加，「對 X 狀態的敵人」判為利用，「不會被 X」「免疫 X」判為抵抗;都不符合時判為其他。
- 覆寫檔以敘述文字的雜湊加關鍵字為鍵，記錄效果類型與是否已複核。建置時覆寫優先於規則。
- 建置會列出雜湊還不在覆寫檔裡的配對，作為待複核清單。維護者在 Claude Code session 裡讓 LLM 逐筆複核，再寫回覆寫檔。這個流程不呼叫任何外部 API。第一次建置時，所有配對都要複核。

### 伺服器文字選擇

- 台服模式:只收錄台服幹員表中存在的幹員與召喚物，比對與顯示都用台服資料。
- 陸服模式:收錄所有陸服幹員，比對用陸服資料。顯示時，台服同一段敘述(同一個技能、天賦或特性的同一個階段)的術語 key 與填入後的數值都和陸服一致時，改用台服文字;否則顯示陸服簡中。
- 模組3 階段:台服沒有模組戰鬥資料，文字與數值一律取陸服簡中並標「陸服資料」;台服模式只列台服模組清單中已實裝的模組。
- 幹員名用台服名，台服沒有該幹員時用陸服名。

### 查詢

- 查詢是純函式:輸入索引與查詢條件(已選關鍵字、效果類型、伺服器、星級、職業與分支)，輸出排好序的幹員清單，每位幹員附上命中敘述。
- 多關鍵字為 AND:每個已選關鍵字都要在該幹員身上至少有一段效果類型符合勾選的命中敘述。不同關鍵字可以來自不同的敘述。
- 任一階段命中就算命中。命中敘述同時帶出兩個階段的文字，並標出只在哪個階段出現。
- 排序依序是星級高到低、職業(遊戲內職業順序)、實裝新到舊。

### 介面

- 關鍵字面板:分組顯示，可以打字過濾、可以複選，也有一鍵清除。手機上收合成抽屜。
- 篩選列:伺服器切換、效果類型複選(預設只勾施加)、星級、職業與分支。上次選的伺服器記在瀏覽器裡。
- 結果卡:頭像、名字、星級、職業，以及命中敘述清單(敘述來源、模組名、階段並列、效果類型、關鍵字高亮)。
- 懸停或點擊高亮詞與關鍵字按鈕時顯示定義:術語用官方定義，補充關鍵字用清單定義，並標「非官方」。點擊命中敘述中的高亮詞會加入或移出該關鍵字。
- 頁尾顯示資料版本。

## 測試決策

- 好的測試只驗證外部行為:給定原始資料與查詢條件，驗證使用者會看到的結果(哪些幹員、什麼順序、哪段敘述、什麼效果類型、什麼文字)。不驗證解析器內部結構或索引的欄位排列。
- **唯一的測試接縫:建置 → 查詢。** 測試餵入手寫的小型原始資料片段(陸服與台服各一份，只放案例需要的幹員、技能、術語)與小型覆寫檔、補充關鍵字清單，執行索引建置，再對產出的索引執行查詢，只斷言查詢結果。
- 要涵蓋的案例:
  - 巢狀標記、包住【】的術語標記、不是標記的角括號、各種佔位符格式。
  - 召喚物歸屬、阿米婭形態、多模組各自比對、只在專精3 或只在模組3 出現的效果、沒有專精的技能。
  - 規則判定的施加、利用、抵抗、其他，以及覆寫檔優先於規則。
  - 多關鍵字 AND、效果類型複選、星級與職業篩選、排序。
  - 台服模式排除未實裝幹員;陸服模式在台服文字一致時用繁中、不一致或缺少時用簡中。
  - 補充關鍵字比對簡中與繁中，且不重複計算術語標記內的文字。
  - 待複核清單只列新增或變動的配對。
- 介面另外用一個 Playwright 煙霧測試:開啟打包後的網頁，點一個關鍵字，看到至少一張結果卡，切換伺服器後結果更新。
- 測試框架用 Vitest。repo 目前是空的，沒有既有測試可以參照。

## 不在範圍內

- 基建技能、敵人、關卡資料。
- 陸服與台服以外的伺服器(英、日、韓)，以及簡轉繁自動翻譯。
- 等級7與專精3以外的技能等級、模組1與模組2、潛能1以外的天賦數值切換(潛能加成只以「A(+B)」呈現)。
- 幹員詳細頁、幹員名稱搜尋、帳號與收藏功能。
- 部署到 GitHub Pages 的設定與發布(使用者自行處理)。
- 後端伺服器、定時自動更新(例如 GitHub Actions)、對外部 LLM API 的呼叫。
