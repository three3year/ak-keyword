# 規格:資料更新流程

Status: ready-for-agent

## 需要你決定的

### 建置失敗時怎麼辦?

例如新幹員的國服名與其他幹員重複、又沒有在 PRTS 頁名清單指定頁名,建置會直接失敗。

決定(2026-10-19):一律停下問你。

- 由 agent 查 PRTS 實際頁名並補上(建議):agent 到 PRTS 確認該幹員的實際頁名,寫進 PRTS 頁名清單後重新建置,摘要裡標出補了哪些。只有查不到或錯誤不是頁名問題時才停下問你。
- 一律停下問你:流程中斷,回報錯誤訊息,由你決定怎麼補。最保險,但每遇到一次就要你介入。

### 上游沒有新版時怎麼辦?

決定(2026-10-19):回報「已是最新」就停下;你說「強制」時照樣完整跑。

- 停下,可強制跑(建議):省時間。
- 一律完整跑:多半是沒有實質變化的一輪。

### 效果類型複核要給你看多少?

決定(2026-10-19):每一筆都列給你看,你確認後才寫進覆寫檔。

- 只看沒把握的(建議):其他直接套用。
- 全部列給我看:最精準,但大版本可能上百筆。
- 全部自動套用:錯了之後再手動修正。

### 新術語怎麼處理?

決定(2026-10-19):由 agent 依官方定義建議放哪一組、哪一行,寫進關鍵字分組,摘要裡標出來給你確認。

- 停下來問你:面板整齊,但每次都要你回答。
- 先放未分組,摘要提醒:不打斷流程。
- 由 agent 建議位置:寫進檔案並在摘要標出。

### 建置警告怎麼處理?

決定(2026-10-19):加一份納入版控的已知警告清單,只回報清單裡沒有的新警告。

- 加已知警告清單,只報新的(建議):已知的上游問題不再重複出現。
- 每次全部列出:新的問題容易被淹沒。
- 只報數量:容易漏掉真正的問題。

### 只有下載時間變了要不要 commit?

決定(2026-10-19):照樣 commit,commit 訊息註明上游版本沒有更新。

- 不 commit,還原索引(建議):不產生內容沒變的 commit。
- 照樣 commit:網頁上的下載時間會更新,看得出最近檢查過。

## 問題陳述

上游國服大約每一兩週更新一次資料版本,台服比較慢。現在要更新資料,維護者得自己照 README 把幾個步驟串起來:下載建置、看待複核配對、在 session 裡讓 LLM 判定效果類型、寫判定檔、套用覆寫、重新建置、跑測試、commit。每一步都要記得指令和檔案位置,漏一步就可能出錯:例如忘了複核,新幹員的效果在搜尋結果裡就查不到。

另外有三件事目前沒有任何提示:

- 上游有沒有新版,要自己去比對版號。
- 遊戲新增的術語會悄悄出現在關鍵字面板的「未分組」,例如現在的 Fever(Ave Mujica 聯動)就在那裡。
- 建置警告每次都會把已知的上游問題重新列一遍(目前 6 則,都是上游敘述少了結尾的標記),真正新的問題容易被淹沒。

## 解決方案

新增一個專案 skill「/update-data」,在 Claude Code session 裡一個指令就跑完整個資料更新:

1. 比對上游與目前索引的資料版本。兩服都沒有新版就回報「已是最新」並停下,除非維護者說要強制跑。
2. 下載並建置索引。
3. 把所有待複核配對交給 LLM 判定效果類型,每一筆都列給維護者確認,確認後寫進覆寫檔,再重新建置,直到待複核清單是空的。
4. 新術語由 agent 依官方定義建議放進哪一組、哪一行,寫進關鍵字分組。
5. 只回報已知警告清單裡沒有的新警告,並說明影響;上游已經修好的警告從清單移除。
6. 跑單元測試、打包、e2e 煙霧測試,全部通過。
7. 給維護者一份摘要,把整次更新放在一個 commit,訊息寫上版號。不 push。

skill 建好後,強制完整跑一次當作演練。預計的改動是下載時間更新、Fever 放進分組、建立第一份已知警告清單。README 的「更新遊戲資料」改成指向這個 skill。

## 使用者故事

1. 身為維護者,我想用一個指令完成整個資料更新,這樣不用記每一步的指令和檔案位置。
2. 身為維護者,我想讓流程一開始先比對上游與索引的資料版本,這樣上游沒有新版時不用白跑一輪。
3. 身為維護者,我想在上游沒有新版時看到「已是最新」和兩服目前的版號,這樣確定不需要更新。
4. 身為維護者,我想在說「強制」時,即使上游沒有新版也照樣完整跑,這樣可以補上頭像或驗證流程。
5. 身為維護者,我想讓國服與台服分開判斷有沒有新版,這樣只有其中一服更新時也看得出來是哪一服。
6. 身為維護者,我想讓上游版號與索引版號只要不同就算有新版,這樣不會因為版號格式特殊而漏掉更新。
7. 身為維護者,我想讓每一筆待複核配對都附上幹員、敘述來源、關鍵字、規則判定和敘述原文,這樣我能逐筆確認 LLM 的效果類型判定。
8. 身為維護者,我想在確認之前,判定都不寫進覆寫檔,這樣錯的判定不會進到搜尋結果。
9. 身為維護者,我想改掉某幾筆判定後再套用,這樣不用為了一筆錯誤整批重來。
10. 身為維護者,我想讓流程套用判定後重新建置,並確認待複核清單是空的,這樣不會有效果在搜尋結果裡漏掉。
11. 身為維護者,我想讓遊戲新增的術語由 agent 依官方定義建議放進哪一組、哪一行,這樣關鍵字面板不會累積在「未分組」。
12. 身為維護者,我想在摘要裡看到每個新術語被放在哪裡、以及理由,這樣我能確認或改位置。
13. 身為維護者,我想在 agent 判斷新術語談不上效果類型時(例如隊伍名),讓它建議放進不當關鍵字的清單,這樣面板不會出現沒意義的關鍵字。
14. 身為維護者,我想讓已知的上游問題記在一份納入版控的已知警告清單,這樣每次建置不會重複看到同樣的警告。
15. 身為維護者,我想只看到已知清單裡沒有的新警告,這樣新的問題不會被舊警告淹沒。
16. 身為維護者,我想讓每則新警告附上影響說明(例如某位幹員某段敘述的關鍵字沒有高亮),這樣我能判斷要不要處理。
17. 身為維護者,我想在確認新警告是上游問題後,把它加進已知清單,這樣下次不再出現。
18. 身為維護者,我想讓上游已經修好、這次沒再出現的已知警告自動被指出並從清單移除,這樣清單不會越積越多。
19. 身為維護者,我想讓 commit 前一定通過單元測試、打包和 e2e 煙霧測試,這樣推上去的網站一定能用。
20. 身為維護者,我想讓第一次跑 e2e 前缺少的瀏覽器由流程自動安裝,這樣不會卡在環境問題。
21. 身為維護者,我想在建置或測試失敗時讓流程停下來回報錯誤訊息,不要自行修補、不要 commit,這樣由我決定怎麼補,壞掉的資料也不會進版控。
22. 身為維護者,我想在 commit 前看到一份摘要:兩服的新舊版號、新增幹員、新術語、複核筆數、新警告、測試結果,這樣一眼就知道這次更新了什麼。
23. 身為維護者,我想讓整次更新放在一個 commit,訊息寫上兩服版號,這樣要退回整次更新很簡單。
24. 身為維護者,我想在上游沒有新版、強制跑完只有下載時間變了時,照樣 commit,並在訊息註明上游版本沒有更新,這樣網頁上的下載時間能反映最近一次檢查。
25. 身為維護者,我想讓流程只 commit、不 push,這樣什麼時候上線由我決定。
26. 身為維護者,我想在 README 的「更新遊戲資料」看到指向這個 skill 的說明,這樣日後回來看文件就知道該怎麼更新。
27. 身為維護者,我想讓 README 手動步驟仍然保留(或指向等價指令),這樣不在 Claude Code session 時也能手動更新。
28. 身為玩家,我想在新幹員實裝後不久就能在搜尋結果找到他們,這樣查到的資料跟得上遊戲。
29. 身為玩家,我想在關鍵字面板看到新術語被放在合理的分組,而不是「未分組」,這樣找得到它。
30. 身為玩家,我想在網頁頁尾看到資料版本與最近一次下載時間,這樣知道資料有多新。

## 實作決策

- **新的專案 skill「/update-data」**:放在專案的 Claude Code skills 裡,寫成 agent 照著做的步驟,把現有的建置、複核套用、測試指令串起來,並寫明每一步什麼時候要停下來問維護者:效果類型複核的確認、新警告的判斷、建置失敗(回報錯誤訊息,不自行修補維護者清單)、測試失敗。
- **比對上游版本**:新增一個維護者指令,下載兩服上游的版本資訊(只抓含資料版號的那個檔),和目前索引的資料版本比對,印出每個伺服器的舊版號、上游版號,以及有沒有新版。比對本身是不連網的純函式:輸入兩邊的版號,輸出哪些伺服器有新版;版號字串只要不同就算有新版(兩服各自比較,彼此不比較)。
- **已知警告清單**:維護者清單新增一份納入版控的已知警告清單,內容是警告全文的列表。建置索引的輸入多一份已知警告清單;輸出除了全部警告,另外分出「新警告」(清單裡沒有的)和「已消失的已知警告」(清單裡有、這次沒出現的)。比對用警告全文,一字不差才算同一則。
- **建置指令的輸出**:建置後除了現有的全部警告檔,另外寫出新警告與已消失警告,主控台摘要也分開列出數量。
- **更新已知警告清單**:提供一個指令,把清單改成「目前全部警告」:也就是把確認過的新警告加入、已消失的移除。skill 在維護者確認新警告都是上游問題後執行它,不讓 agent 手抄警告全文。
- **新術語**:沿用現有規則,沒列在關鍵字分組的術語會進「未分組」。skill 從建置後的索引讀出「未分組」裡的術語,依官方定義提出位置,寫進關鍵字分組,或建議放進不當關鍵字的術語清單。
- **效果類型複核**:沿用 ADR 0001 的流程(規則判定 + session 內 LLM 複核 + 覆寫檔),不呼叫外部 API。差別只在 skill 把每一筆判定列給維護者看,確認後才寫成判定檔、用現有的套用指令寫進覆寫檔。
- **commit 訊息**:有新版時寫「data: 更新至國服 X、台服 Y」;強制跑且版號沒變時寫明上游版本沒有更新,例如「data: 重新建置(上游版本未更新:國服 X、台服 Y)」。
- **演練**:skill 完成後強制完整跑一次,本身就是這份規格的驗收。

## 測試決策

- 好的測試只看外部行為:給定輸入,檢查輸出,不測內部怎麼做。
- **建置索引這一層**(現有的切入點,現有測試都從這裡切入):用假資料造出會產生警告的敘述(例如沒有關閉的標記),給定一份已知警告清單,檢查輸出的「新警告」只有清單裡沒有的、「已消失的已知警告」只有這次沒出現的;已知清單為空時全部警告都是新警告。前例是現有建置與查詢的 Vitest 測試和共用的假資料工具。
- **版號比對**:測不連網的純函式。案例包括兩服都沒變、只有國服變、只有台服變、兩服都變、索引沒有台服資料的情況。
- **新術語進「未分組」**:現有測試已涵蓋,不加新測試。
- **下載上游版本資訊**和 **skill 整體流程**:不寫自動測試,由演練實際跑一次驗證。
- 現有的單元測試與 e2e 煙霧測試全部要繼續通過。

## 不在範圍內

- 自動偵測上游新版並通知(GitHub Actions 排程、雲端排程 agent)。維護者想到時再跑。
- 在 GitHub Actions 上跑資料更新或自動部署新資料。效果類型複核需要 session,而且依 ADR 0002,沒複核的配對不會出現在搜尋結果。
- 自動 push。push 一律由維護者自己做。
- 修正上游資料本身的問題(例如沒有關閉的標記)。這些記進已知警告清單。
- 更新已存在的頭像圖檔。建置只補缺少的頭像。
